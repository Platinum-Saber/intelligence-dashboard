# FinBERT Buyer-Perspective Fine-Tuning Guide

**Project:** ACL Cables PLC — Procurement Intelligence Dashboard  
**Last tuned:** 2026-05-15  
**Current model:** `FinBERT_model/model/buyer_finbert/`  
**Base model:** `ProsusAI/finbert`

---

## 1. Why This Exists

The dashboard uses FinBERT to score financial news sentiment for procurement decisions. The base FinBERT model (`ProsusAI/finbert`) was trained on the Financial PhraseBank dataset with labels assigned from a **trader/investor perspective**:

- "Copper prices surge" → `POSITIVE` (good for traders long on copper)
- "Copper mine strike" → `NEGATIVE` (supply shock, bad for traders)

From a **procurement buyer's perspective**, these are reversed:

- "Copper prices surge" → `NEGATIVE` (costs more to buy)
- "Copper mine strike" → `NEGATIVE` (supply risk AND price pressure — still negative, but FinBERT gets this right by accident)
- "New copper mine opens" → `POSITIVE` (more supply → prices ease) — **FinBERT gets this wrong** (says POSITIVE for wrong reason, and current inversion would flip it to NEGATIVE)
- "ACL secures fixed-price copper contract" → `POSITIVE` — **FinBERT inversion gets this wrong**

### The Original Workaround

`sentiment_service.py` had a post-inference label flip (`_buyer_key()`) that inverted POSITIVE↔NEGATIVE for COPPER and ALUMINIUM topics. This is blunt — it works for price-movement articles but misclassifies:
- Supply disruption articles (FinBERT says NEGATIVE, inversion flips to POSITIVE — wrong)
- New supply source articles (FinBERT says POSITIVE, inversion flips to NEGATIVE — wrong)
- Procurement deal articles (FinBERT says POSITIVE, inversion flips to NEGATIVE — wrong)

### The Fix

Fine-tune FinBERT's classification head on procurement-buyer-labeled data so the model learns the correct perspective directly, eliminating the need for the blunt inversion.

## 2. Architecture Decision — Option 2: Frozen Encoder

**What was chosen:** Freeze all 110M BERT encoder parameters. Retrain only the final classification head (`model.classifier` — a single `Linear(768, 3)` layer).

**Trainable parameters:** 2,307 out of 109,484,547 (0.002%)

**Why this over alternatives:**

| Option | Trainable Params | Chosen? | Reason |
|--------|-----------------|---------|--------|
| Full fine-tuning | 110M | No | Requires 10,000+ examples; overfits badly on small datasets |
| Option 2 — head only | ~2,300 | **Yes** | Safe for 300–500 examples; fast on CPU; near-impossible to overfit |
| Option 2.5 — head + last BERT layer + pooler | ~7.7M | No (yet) | Better for edge cases but needs 800–1,000+ examples to avoid overfitting |
| LLM prompt-based | 0 | No | High latency (~1–2s/article), API cost per inference, internet dependency |

**When to upgrade to Option 2.5:** When the combined dataset (synthetic + real) exceeds ~800 examples. See Section 7.

**Label mapping** (must match `ProsusAI/finbert` original config exactly for drop-in compatibility):

```
negative → 0
neutral  → 1
positive → 2
```

## 5. API Configuration

Both keys are stored in `FinBERT_model/.env`:

```
FREENEWSAPI_KEY=<freenewsapi.io key>   # 5,000 req/day, 2 req/sec, no pub delay
ANTHROPIC_API_KEY=<anthropic key>       # Used by auto_label.py via Claude Haiku
```

### freenewsapi.io Details

- Base URL: `https://api.freenewsapi.io/v1`
- Auth: `x-api-key` header (not query param)
- `/v1/news` response structure: `{"data": [...articles...], "meta": {"has_more": bool, "next_offset": int, ...}}`
- `/v1/details` response structure: `{"data": {"uuid": ..., "title": ..., "body": ..., "incipit": ..., "original_url": ..., "published_at": ..., "publisher": "string"}}`
- **Critical:** Both endpoints wrap their payload under a `"data"` key. The `publisher` field is a plain string, not an object.
- Request delay: 0.6s between calls (stays under 2 req/sec rate limit)

### Claude Sonnet Labeling

Model: `claude-sonnet-4-6`  
The system prompt instructs the model to act as a procurement buyer and classify from buyer perspective. It handles the nuance that a blunt inversion cannot — supply disruptions, procurement deals, new supply sources are all classified correctly by context rather than keyword inversion.

**Why Sonnet, not Haiku:** Run 1 used Haiku and demonstrated clear failures on ambiguous articles — near-duplicate BHP articles received opposite labels (`negative` vs `positive`) because Haiku couldn't consistently distinguish "mining company stock news" from "copper price news". The cost difference for a 250-article batch is ~$0.17 (Haiku $0.03 vs Sonnet $0.20) — negligible for an infrequent operation where label quality directly determines model quality.

## 6. How to Re-Tune (Standard Run)

### Prerequisites

Ensure both API keys are set in `.env`. Run from the `FinBERT_model/` directory.

### Full Pipeline (Recommended)

```bash
cd "d:/Projects/Intelligence Dashboard/FinBERT_model"
uv run python model_tune.py
```

This runs all 5 steps:
1. Regenerate `synthetic_labeled.csv` from `synthetic_data.json`
2. Fetch new real articles from freenewsapi.io
3. Auto-label new articles via Claude Haiku (skips already-labeled UUIDs — safe to re-run)
4. Merge all sources into `training_dataset.csv`
5. Fine-tune and save model to `model/buyer_finbert/`

### Train Only (Dataset Already Exists)

Use this when you have already collected real data and only want to retrain:

```bash
uv run python model_tune.py --skip-data
```

### Fetch + Label Only (No Training)

Use this to accumulate more data without overwriting the current model:

```bash
uv run python fetch_news.py
uv run python auto_label.py
```

Then run `model_tune.py --skip-fetch` when ready to retrain.

### Custom Hyperparameters

```bash
uv run python model_tune.py --epochs 8 --lr 1e-4 --max-per-topic 80
```

Default hyperparameters (Option 2):
- `--epochs`: 5
- `--batch-size`: 16
- `--lr`: 2e-4 (higher than full fine-tuning; only 2,307 params to train)
- `--max-per-topic`: 50 (fetches up to 50 articles per topic)

## 7. Quality Benchmarks and Upgrade Path

### Run 1 (2026-05-15) — Haiku-labeled data

| Epoch | Loss | Val Accuracy | Negative | Neutral | Positive |
|-------|------|-------------|----------|---------|----------|
| 1 | 2.096 | 18.8% | 9/36 | 3/13 | 1/20 |
| 2 | 1.168 | 56.5% | 34/36 | 0/13 | 5/20 |
| 3 | 0.981 | **63.8%** ✓ | 32/36 | 5/13 | 7/20 |
| 4 | 0.915 | 62.3% | 30/36 | 6/13 | 7/20 |
| 5 | 0.896 | 63.8% | 30/36 | 6/13 | 8/20 |

Dataset: 344 examples (200 synthetic + 144 real). Labels from Claude Haiku — inconsistent on ambiguous mining stock articles.

### Run 2 (2026-05-15) — Sonnet-labeled data (current model)

| Epoch | Loss | Val Accuracy | Negative | Neutral | Positive |
|-------|------|-------------|----------|---------|----------|
| 1 | 2.010 | 21.7% | 9/34 | 5/16 | 1/19 |
| 2 | 1.133 | 50.7% | 31/34 | 0/16 | 4/19 |
| 3 | 1.003 | 53.6% | 27/34 | 4/16 | 6/19 |
| 4 | 0.959 | **58.0%** ✓ | 28/34 | 6/16 | 6/19 |
| 5 | 0.964 | 58.0% | 28/34 | 6/16 | 6/19 |

Dataset: 344 examples (200 synthetic + 144 real). Labels from Claude Sonnet 4.6 — higher quality.  
Label distribution: negative: 177 / neutral: 75 / positive: 92

**Why Run 2 accuracy (58%) is lower than Run 1 (63.8%):**  
Sonnet correctly classified more articles as neutral (55 vs 43 by Haiku), particularly mining company stock news and macro articles with no direct buyer impact. The neutral class is harder to learn (requires understanding that an article is *not* about copper price or supply), so the model faces a harder task with better-quality labels. The 58% figure is on genuinely harder examples — the labels are more trustworthy, not less.

**Baselines for context:**
- Random chance: 33%
- Majority-class (always predict "negative"): 51.5% (177/344)
- **Run 2 model: 58.0%** — above both baselines on higher-quality labels

**Positive class weakness:** 6/19 correct (31.6% recall). Root cause is real data class imbalance (only 10 positive out of 152 Sonnet-labeled real articles — copper was at record highs on collection date). Will self-correct as more articles are collected across different market conditions.

### When to Re-Tune

Re-tune when any of the following apply:
- `real_labeled.csv` has grown by 100+ new rows since the last training run
- Market conditions have shifted (e.g., copper prices dropped significantly — will add positive articles)
- The dashboard team reports misclassifications on specific article types

### When to Upgrade to Option 2.5

When `training_dataset.csv` has 800+ total rows AND the positive/neutral class recall is still below 50%, upgrade to Option 2.5 by unfreezing the last BERT layer and pooler in addition to the classifier.

In `model_tune.py`, find the freeze block and add:

```python
# Freeze all parameters, then unfreeze classifier head (Option 2 — current)
for param in model.parameters():
    param.requires_grad = False
for param in model.classifier.parameters():
    param.requires_grad = True

# ADD THESE LINES for Option 2.5 (when dataset > 800 examples):
for param in model.bert.encoder.layer[11].parameters():
    param.requires_grad = True
for param in model.bert.pooler.parameters():
    param.requires_grad = True
```

Option 2.5 trainable parameters: ~7.7M out of 110M (~7%). Lower the learning rate to `5e-5` when using Option 2.5 to prevent the BERT layers from catastrophic forgetting.

## 8. Wiring the Model into the Dashboard

After each training run, the saved model at `model/buyer_finbert/` is a drop-in replacement for `ProsusAI/finbert`. One change required in the backend:

**File:** `backend/app/services/sentiment_service.py`

```python
# Change this line in _get_pipeline():
_pipeline = pipeline(
    "sentiment-analysis",
    model="ProsusAI/finbert",   # ← before
    ...
)

# To:
_pipeline = pipeline(
    "sentiment-analysis",
    model=r"D:\Projects\Intelligence Dashboard\FinBERT_model\model\buyer_finbert",  # ← after
    ...
)
```

No other changes are needed. Label IDs (negative=0, neutral=1, positive=2) match the original FinBERT config exactly.

**Important:** Once the fine-tuned model is wired in, the `_buyer_key()` inversion function in `sentiment_service.py` should be disabled — the model now encodes buyer perspective directly. The DB stores buyer-correct labels either way, so existing data remains valid.

To disable the inversion after switching models, change `score_unscored_news()` in `sentiment_service.py`:

```python
# Before (with inversion)
row.sentiment = _buyer_key(row.topic or "", raw.lower()).upper()

# After (model already outputs buyer-correct labels — no inversion needed)
row.sentiment = raw.upper()
```

## 9. Known Issues and Decisions

| Issue | Decision | Rationale |
|-------|----------|-----------|
| freenewsapi.io returns articles under `"data"` key, not `"news"` | Fixed in `fetch_news.py` | Discovered on first run; both `/v1/news` and `/v1/details` wrap under `"data"` |
| `publisher` field is a plain string, not `{"name": "..."}` | Fixed in `fetch_news.py` `build_article()` | API docs implied object; actual response is string |
| Real data class imbalance (negative-heavy) | No resampling applied | Imbalance reflects real market state; synthetic data compensates with balanced classes; will self-correct over time |
| Sri Lanka-specific FX queries return 0 articles | Known limitation | "LKR dollar", "Sri Lanka rupee" return no results; "rupee exchange" returns Indian rupee articles too. FX data is carried mostly by synthetic examples. |
| `real_labeled.csv` accumulates across runs | Intentional | `auto_label.py` deduplicates by UUID; old labels are never overwritten; the file grows safely with each fetch run |
| HuggingFace unauthenticated warning during training | Cosmetic | Model loads from cache after first download; warning can be suppressed by setting `HF_TOKEN` env var if needed |
| Python 3.14 used instead of 3.12 | No action needed | uv picked up system Python 3.14; all dependencies are compatible |
